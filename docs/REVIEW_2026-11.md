## What looks sound (checked, no finding)

- The allow-list and the six All writers: no seventh path found; formula cells are read and refused before each write.

# Part A: data safety

## Critical

### A1. Staging folder listing stops at Graph's first page, so a CollectionID in use can be handed out again
- **What happens.** `listChildren()` (L9937) asks for a folder's children once and never follows `@odata.nextLink` (the word `nextLink` does not occur in app.html). Three callers list `CoinCollection/Staging`: `readMaxReservedIdFromStaging()` (L13544, the CollectionID reservation), `listCoinDrafts()` (L13926) and `listSetDrafts()` (L13662). Past one page, the newest folders are not seen. The reservation then returns "highest on All + 1", which can be the id of a draft that is in Staging and not yet on All. `writeCoinDraft()` (L13919) uses `uploadJson`, which has no no-overwrite option, so the new coin's `coin.json` replaces that draft's. Its photos then fail with 409 (same names) and are dropped (A2).
- **Trigger.** More Staging folders than one Graph page. Every coin or Set saved through the app adds a folder and none is ever removed ((aa) Staging cleanup is not built), so the count only grows.
- **Data at risk.** A whole pending draft (its fields); the new coin's photos; two coins sharing one CollectionID. Also: drafts beyond the page vanish from Staging Review, and the launch retry of a promoted coin's file move never sees them.
- **How likely.** Certain once the count passes the page size; not at all before. Microsoft documents 200 as the default page size for a folder's children, and names are normally returned in ascending order, which cuts off exactly the newest ids. **Suspected** on those two points (not checked against Graph here); **confirmed in code** that there is no paging and that the draft write overwrites.
- **Ray can check today:** the number of folders in `CoinCollection/Staging` on LIVE (and in `_Testing/Staging`). Under about 150 there is time; near 200 this is urgent.
- **Fix.** (1) Follow `@odata.nextLink` in `listChildren()` and ask for `$top=999` (S). (2) Write a NEW draft's first `coin.json` / `set.json` with `conflictBehavior=fail`, so a reservation that collides stops loudly instead of overwriting (S). (3) A suite with 250 mock folders. Total S. Building the Staging part of (aa) lowers the count but is not the fix.

## High

### A2. Add Coin's first save drops any photo or receipt that fails to upload
- **What happens.** `completeAddCoinSaveUntimed()` (L36563): `uploadCoinDraftPhotos()` (L36479) catches each failed upload and lists it; the draft is written with only the photos that landed plus a research note; then `resetAddCoinAfterSave()` runs `resetAddCoinForm()`, which deletes `galleryStore[ADDCOIN_GALLERY_ID]` and the receipt pick. The failed picks, and the crop work on them, are gone. With Save to Database the coin then goes on to All without them. The toast says "1 file(s) didn't upload — see the draft's research note".
- **Trigger.** Any upload failure during the first save: a weak signal, a 409, a 5xx. More likely since (ak): a Holder photo is now up to about 12 MB.
- **Data at risk.** The cropped photo and the crop itself. A photo taken with the camera from inside the app may exist nowhere else. The coin's fields are safe.
- **How likely.** Moderate over time on a phone. **Confirmed by run** (probe P3: one failed upload, draft saved with `photos: []`, pick count 1 before and 0 after).
- **Note.** The Staging-draft EDIT path already does this properly (`saveCoinDraftEdit`, L36737: "Nothing was recorded — everything is still here"). Only the first save loses the pick. docs/ref/ADD_COIN_WRITE.md says "A single file failing never loses the capture"; that is true of the draft, not of the file.
- **Fix.** After a save with failed files, open the saved draft in the existing Staging-draft edit mode with the failed picks still in place, so Save again retries them (reuses `uploadStagingEditFiles`). M. Until then, S: do not reset the form when anything failed.

### A3. Promote: a Photos or Receipts row that fails to write is silent and never retried
- **What happens.** `movePromotedCoinFiles()` (L14230): once every file has moved it calls `recordPromotedCoinRecords()` (L14255), which catches each row failure into `out.failed` and `console.warn`s it. Nothing reads `out.failed`. The next line sets `filesMovedOnPromotion = true`, so the launch retry (`processPromotedCoinDrafts`, L14298) skips the draft for good. `finishCoinDraftWrite()` (L25908) ignores the function's result. The same code shape is in `movePromotedSetFiles()` (L14898).
- **Result.** The file is in CoinPhotos with no Photos row. The Photos tab is the only record, so the coin shows no photo and nothing says why.
- **Also:** a file move that is REFUSED (a different file already at that name) leaves the photos in Staging and retries at every launch, with nothing on screen, ever.
- **Trigger.** One failed workbook write among the roughly ten requests each Photos row costs (B3) during a Promote: a 429 / 5xx, a session change, the read-only gate (A6).
- **Data at risk.** No file is lost; the link from the coin to its photos and receipt is. Recoverable by hand only if noticed.
- **How likely.** Low per Promote, moderate over a year of Promotes. **Confirmed by run** (probe P1: Photos write failed, file moved, zero Photos rows, flag true, the only toast was the success one).
- **Fix.** Set the flag only when `records.failed` is empty; otherwise leave the draft for the launch retry and say so in the toast and on the Docket. Before that, make the row write safe to repeat (A5's fix), or a retry duplicates rows. S to M together with A5.

### A4. Reject can delete the only photos of a coin that is already on All
- **What happens.** `performRejectStagedCoin()` (L26429) refuses only when the draft's own `allRowWritten` flag is set, then deletes the whole `Staging/{id}` folder. After a Promote that wrote the All row but could not write the draft's status (`finishCoinDraftWrite` throws after two tries; toast "is on the All sheet, but tidying up afterwards failed"), the flag is still false, the photos are still in Staging (the move comes after the status write), and the in-memory coin list has not been refreshed, so Staging Review still shows the draft with a Reject button.
- **Data at risk.** That coin's photos and receipt. They go to the OneDrive recycle bin, so they are recoverable for a while if noticed.
- **How likely.** Low: it needs the failure and then a tap on Reject in the same session. **Confirmed by run** (probe P2: row on All at row 3, draft still "Ready for reconciliation", Reject deleted the folder, no copy in CoinPhotos).
- **Also wrong:** that toast ends "photos retry at next launch". The launch retry only looks at drafts whose status is Promoted (L14304), so in this state, and after any Force Add (its patch never sets Promoted, L26089), nothing retries.
- **Fix.** In `performRejectStagedCoin`, look the id up on All fresh (`findAllSheetRowNumber`) and refuse if it is there (S). Make the launch retry cover `allRowWritten && !filesMovedOnPromotion` whatever the status, with the same duplicate-row care as A3 (S).

## Medium

### A5. A photo save that lands but reports failure leaves two Photos rows for one file on the next Save
- **What happens.** A new Photos row is two requests: `patchRecordRow()` (L12578) writes the row, then a second PATCH sets the DateAdded date format. If the second fails (or its answer is lost, or the session changes between them), the save reports failure although the row is there. On Save again, a repeatable type (Reference, Other, COA, Package) has nothing to find its earlier row by, so `writePhotoRowInStep()` (L12680) claims a new row with a new PhotoID. Non-repeatable types (Obverse, Reverse, Holder) are safe: they find their row by type and update it.
- **Same shape at launch:** if `recordPromotedCoinRecords` succeeds and the draft write after it fails, the next launch records the rows again.
- **Data at risk.** No loss. A duplicate row: the photo shows twice; removing or purging one leaves the other pointing at a file that Purge may then delete.
- **How likely.** Low. **Confirmed by run** (probe P4: first Save "failed", second "ok", rows PH-00001 and PH-00002 both on `AY-00001_reference_01.jpg`, one file).
- **Fix.** (1) Before claiming a row for a repeatable photo, look for a row with the same CollectionID and Filename and reuse it. (2) Send the date format in the same `$batch` as the row, so the row is one request. Both S; (2) also saves a round trip per photo.

### A6. A save can be refused part-way: the write gate and the workbook session are checked per request, not per save
- **What happens.** `gatedGraphClient()` (L7414) asks `workbookWritesAllowed()` before EVERY write, uploads included. The connection state can change during a save: the `offline` event (L7643), or a version check on resume that times out (`maybeCheckOnResume` calls `checkSessionAgainstWorkbook`, L7520; it runs when the app becomes visible again, for example on return from the camera, and has no "a save is running" guard). A background read can also drop the Excel session (`excelWorkbookFetch`, L9743), which raises the generation; the save's next workbook write is then refused as SESSION_CHANGED, and a step that has already written does not re-run (L7397).
- **Result.** A photo save is upload, then several reads, then the row write. A refusal in the middle gives "file uploaded, row not written, save reported failed". Save again completes it (`entry.uploadedNames` skips the upload), so nothing is lost, but it is the symptom in (bw), and for repeatable photos it feeds A5.
- **How likely.** Occasional on a weak signal. **Confirmed in code**; whether it is what happened on 11 Nov is not known (see "The two known leads").
- **Fix.** Do not start a resume / version check while `editSaveInFlight` is true; run it when the save ends (S). Longer term, decide "may this save write" once at the start of a save rather than per request, keeping the per-request check only for offline (M; needs a plan because it touches invariant 17).

### A7. Uploads and workbook writes have no deadline
- **What happens.** `putContent`, `excelWorkbookFetch` and the `$batch` POST are bare `fetch` calls with no abort. A request that never answers leaves Save spinning under the edit-save lock ("Still saving — wait for it to finish") until the app is closed. The save watch (L7183) only measures.
- **Data at risk.** None directly; closing the app mid-save leaves whatever had landed. Every path resumes or retries, subject to A3 and A5.
- **Known:** backlog (ap) 1.5 with 2.4. **This review would raise it**: it is the cheapest cut in "save hung, I closed the app" cases, and the spot-price path already has the pattern (`spotWithTimeout`, "may have written").
- **Fix.** One shared deadline helper for writes; a timeout must report "may have been saved", never "not saved" (see A8). M.

### A8. "Nothing was saved" can be untrue when a workbook write gets no answer
- **What happens.** In `patchWorkbookRanges()` (L10127), when the `$batch` POST throws (no response), `batchWriteError()` (L10927) builds its message from `landed`, which is empty, so it reads "Nothing was saved … Graph said: no response". The batch may have been applied; only the answer was lost. `saveCoinRowToWorkbook()` (L11708) returns reason "error" with that text, nothing is recorded as the app's own write, and the next Save shows a conflict listing the values Ray himself just typed.
- **Data at risk.** None; the message is wrong and the next step is confusing.
- **How likely.** Low, mobile networks. **Confirmed in code.**
- **Fix.** On "no response", re-read the row (as `partialSaveResult()` already does) and report what is actually there; word the fallback "may have been saved". S.

### A9. Edit Coin: a failed CoinID re-link is a toast only, and cannot be retried
- **What happens.** `performBrowseEditWriteLocked()` (L22294): after the fields are saved with a changed identity, `writeCoinIdCell` runs. If it fails, the catch (L22353) adds "(Couldn't update CoinID automatically — worth a manual check.)" to the success toast. The row now has the new identity and the OLD CoinID, nothing goes to the Docket, and the form is clean, so Save again writes nothing.
- **Data at risk.** The coin stays linked to the wrong catalog row (mintage, Fun Fact, metal content, album slot) until someone notices.
- **How likely.** Low. **Confirmed in code.**
- **Fix.** On failure, file the same Docket entry `flagCoinIdNeedsRelink` writes, or keep the form dirty so Save retries the re-link. S.

### A10. Edit Set: typed field changes are not saved (known, (r))
- **What happens.** Edit Set's Save applies the fields to memory only and says "Updated … for this session only — not saved to OneDrive" (L22579). Status, sale details, Value, Cost and notes typed there are gone at the next launch.
- **Honest, but a trap:** it is the one form where typing is thrown away, and the fields look the same as Edit Coin's.
- **Priority change suggested.** Until (r) is built, make those fields read-only with one line saying so (S). No data risk in doing that.

### A11. A wrong-row write after an Excel row change is still undetected (known, (bi)); a cheap detector exists
- **Known gap, not re-argued.** Every All write goes by address after a lookup; nothing checks afterwards.
- **New suggestion.** Put a GET of the target row as the first request of the same `$batch` as the PATCHes (it runs in the same Excel session, in order). After the batch, check that the row it returned holds this CollectionID. If not, the app holds the exact values it just overwrote and can show them, loudly, for a hand repair. This does not prevent the wrong write; it turns a silent one into a loud, recoverable one. M. **Suspected** to work as described: whether a GET inside a batch can itself be stale is the same open question as (bi), and needs a TEST.

### A12. The reservation trusts any folder name in Staging, and `stage.html` creates names that break it
- **What happens.** `reservationIdNumber()` (L13501) is `parseInt` of the name with "AY-" removed; it does not check the shape. A folder whose name starts with digits counts. `stage.html` (L323-324) saves into `CoinCollection/Staging/YYYYMMDD-HHMMSS`. After one use, `parseInt("20261114-213000")` is 20261114 and the app's next CollectionID is `AY-20261115`. That id then fails the app's own `^AY-\d{5}` checks (`photoCommitTargetId`, L30341), so its photos cannot be saved to it.
- **Also:** `stage.html` always writes to the LIVE folders, whatever the build (it has no target check), including when the site is a TEST deploy.
- **Data at risk.** The id scheme; one coin with an 8-digit id on All if Save to Database is used.
- **How likely.** Low: `stage.html` is the old form, still deployed and described as working. A folder Ray makes by hand in Staging with a name like "2026 old" does the same. **Confirmed in code.**
- **Fix.** Count only names that match `^AY-\d{5}$` (S). Ray's call: retire `stage.html` or leave it (it is not linked from the app).

## Low

### A13. Two devices at once
Ray is one user, so these need two devices active within minutes of each other. **Confirmed in code** unless marked.
- `docket.json`: `appendDocketEntry()` (L14824) adds to the copy read at launch and uploads the whole file; a second device's older copy wipes the first's new entries. No eTag check.
- Draft JSON (`coin.json`, `set.json`): whole-file overwrite, same shape.
- Reservation: two devices can be given the same next id; the second's `coin.json` replaces the first's (A1's fix (2) stops this).
- Blank-row claim: two devices can pick the same blank All row; with read lag the window is minutes, not seconds. The second key write replaces the first coin's keys. **Suspected** (depends on how stale the second device's reads are).
- PhotoID / ReceiptID: minted from a column read, so two devices can mint the same one ((u)'s class of problem).
- **Fix.** `If-Match` with the file's eTag on the Docket and draft uploads (S). The rest is what (bp), the single-writer lease, is for; no change of priority suggested.

### A14. An upload whose answer is lost costs two more Saves and leaves an unreferenced copy
`commitGalleryPhoto()` (L30351): the file lands, the answer does not, so the name is not marked uploaded. Save again gets 409 ("already there — nothing was overwritten"); the Save after that picks `_02` and uploads again. **Confirmed by run** (probe P6: three Saves, files `…slab_obverse.jpg` and `…slab_obverse_02.jpg`, one row). Fix: on 409, compare bytes and adopt the file if identical, as receipts do. S.

### A15. Photos / Receipts row updates rewrite the whole row from column A
`patchRecordRow()` (L12578) fills every cell from A to the last header. For an existing row (a receipt replace in `writeReceiptRowInStep`, L13144; a shared-receipt update; Purge's field clear) any column the app does not supply is blanked, a formula in the row would be replaced by a value, and `buildPhotoRowPatch()` (L12820) sends every value back as trimmed text. Harmless with today's columns (Photos 7, Receipts 4, no formulas). **It must be fixed before (ag)** adds ReceiptType / GradingCost, or before Copilot adds any column to either tab. Fix: update only the cells that change, as `replaceFileCells` already does. S to M.

### A16. Add Set drafts: uploads overwrite, and a failed draft write strands a folder
`uploadDraftPhoto()` (L39478) uploads without `NO_OVERWRITE`, so re-taking a Set or child photo replaces the earlier file in Staging (invariant 9's wording says files are never overwritten). In `startSetCapture()` (L39541-39557) the photos upload before `set.json` is written; if that write fails, the folder holds photos and no draft, the id is used up, and trying again reserves a new one. Staging only. S.

### A17. A shared receipt's "all coins" update can stop half-way
`commitReceiptCaptureInStep()` (L28455-28462) writes this coin's row, then each sharing coin's row, one request each. A failure between them leaves one ReceiptID pointing at two files until Save is tapped again, which heals it. Fix: one `$batch`. S.

### A18. The file move checks only that the destination exists
`moveFileWithoutOverwrite()` (L14224) deletes the source once `getItemMeta(dest)` returns anything. Comparing the destination's size with the bytes it sent costs nothing. S.

### A19. Deleting the newest row in Excel lets its id be reused with its old photos
The reservation is max + 1. If the highest-numbered row is deleted from All while its Photos / Receipts rows stay, the next coin gets that id and inherits those rows. Edge case; a Copilot_Rules line ("never delete the newest row without its Photos and Receipts rows") covers it.

### A20. Edit saves go to the first row with that CollectionID
`findAllSheetRowNumber()` (L11053) returns the first match. If All ever holds the same id twice (a pasted or copied row), every later save goes to the first and the second drifts. Promote already counts the rows (`findAllSheetRowNumbersFor`); Edit could refuse when there are two. S.

# The two known leads

### (bw) "Edit Coin save reported failure after the file had uploaded"
The cause cannot be proved from the code: the evidence was overwritten by the retry, as (bw) says. What the code allows, most likely first:

1. **A failure after the upload, inside the Photos-row step.** After `uploadFile` succeeds, `writePhotoRow` makes about ten workbook requests (B3). Any one failing fails the photo. That alone explains "file there, save failed".
2. **The row write itself landed and a later request failed** (A5): the row's values PATCH succeeds and the separate date-format PATCH fails. This fits what was seen better than 1: the retry "wrote the Photos row" and said "replaced", one row, one file. A Holder back finds its own row from the first attempt and updates it, which the app counts as "replaced".
3. **The write gate or the session changed mid-save** (A6).

**A check that can tell 2 from the others:** on the `_Testing` Photos tab, look at PH-00267's DateAdded. If it shows a bare number (about 46337) instead of a date, the format write is what failed and 2 is the cause. If it shows a date, it was 1 or 3 (or the photo already had a row before that save, in which case "replaced" was simply true).

Whatever the cause, three changes make the next occurrence diagnosable and harmless: keep the last several saves' steps instead of one ((bw) as written; `lastSaveTiming`, L7229, holds only the last); put the failure's reason in the toast (`photoSaveFailureText`, L31407, lists file names only; the reason is in `entry.uploadError`); and A5's fix.

### (bv) "Retry said it replaced the file when it only wrote the Photos row"
**Confirmed in code.** `commitGalleryPhoto` skips the upload on a retry because `entry.uploadedNames[filename]` is set (L30398), so there is no upload step. `savePendingPhotos` (L31337) counts the photo as "replaced" whenever `writePhotoRow` returned `replaced: true`, which means only "a row for this photo type already existed and its Filename cell was updated". Nothing wrong was written. Wording fix: count it as "saved" when no file was uploaded in this Save. S.

# Part B: general improvements (ranked by value for effort)

**B1. Say why a save failed, and keep the last several saves.** Raises (bw). Put the reason in the failure toast and keep a short rolling list of save logs in Docket > About (memory only), with a Copy button. Benefit: (bw)-type reports become answerable from one screenshot. Size S. Risk: none (display only).

**B2. Run the suites in parallel.** `tests/run-all.js` runs 102 suites one after another: 822 s. Each suite opens its own browser on a `file://` page, so three or four at a time should bring the merge gate to about four minutes. Benefit: every merge, and it makes a second full run affordable. Size S. Risk: a timing-sensitive suite may wobble; keep a serial switch and compare the sorted PASS / FAIL lines once.

**B3. Fewer round trips per photo save.** Image work is the main use, and each new Photos row costs about ten requests in a row: session, header, the whole Photos table (two requests, read again for a Replace), the id column for minting, the header and the column again inside `writeRecordRow`, a blank-row read, the row PATCH, the date-format PATCH. Four photos is about forty. Read the Photos table once per Save, mint and claim inside one lock, and send row plus format in one `$batch`. Benefit: a multi-photo Save two to three times faster, and fewer places to fail (A3, A5, A6). Size M. Risk: it is write-layer code; keep the lock, the claim and the fresh-header rules, and do it with B6's tests.

**B4. Promote: move files with Graph's move, not download and re-upload.** `moveFileWithoutOverwrite` downloads each Staging file to the phone and uploads it again. With (ak) a Holder photo is up to 12 MB, so Save to Database sends each photo three times (to Staging, back, to CoinPhotos). Graph's move (a PATCH of the item's parent with `conflictBehavior=fail`) is one small request and is atomic. Keep today's byte-compare path for the "name already taken" case. Benefit: a much faster Promote on mobile data. Size S to M. Risk: must stay no-overwrite; needs a real-device TEST of the 409 case. **Suspected** on Graph's exact behaviour for a personal OneDrive.

**B5. Stop re-reading every Staging folder.** `listCoinDrafts` and `listSetDrafts` each GET one JSON per folder, one after another: twice over at every launch, and again after every Add Coin save, Promote and Staging Review. Folders are never removed, so the cost grows with every coin. Skip folders already known to be finished (remember them for the session), fetch the rest a few at a time, and build the Staging part of (aa) (move finished folders to one "done" place). Raises that part of (aa). Benefit: faster launch and Promote, and it holds off A1. Size S to M. Risk: low (reads); the cleanup part moves files and needs Ray's OK.

**B6. A failure-injection suite for the write paths.** The suites cover the happy paths and many refusals well. What found A2 to A5 was failing or losing the Nth request of a flow. One shared mock wrapper ("fail request N", "the answer to request N is lost") run across Add Coin save, Promote, Edit Coin with photos, receipts and Purge, asserting four things each time: no pick lost, no row duplicated, nothing deleted that is still referenced, the message matches what landed. Benefit: catches this whole class before LIVE. Size M. Risk: none (tests only).

**B7. A read-only consistency check.** One Docket screen, GET only: Photos rows whose file is missing; files in CoinPhotos or CoinReceipts with no row; one file on two rows; duplicate PhotoIDs ((u)); coins on All whose photos are still in Staging; drafts whose id is on All; Receipts with two rows for one coin. Benefit: Ray can see damage from any finding above, and from old builds ((v)), instead of finding it by chance. Size M. Risk: none (no writes); listing CoinPhotos needs the paging from A1.

**B8. Crop: start from the last photo's framing.** Slabs shot from the same stand need the same box every time, and today each crop starts at the whole photo (trim-only types) or a default. A "same as last" button (or default) on the rectangle crop that starts the box where the previous photo's ended would turn four handle drags into one tap for a run of coins. It is a cheaper cousin of the deferred auto-fit (Q11), with no detection to get wrong. Display state only; an untouched trim-only photo must still keep its original bytes, so "same as last" has to count as touched. Size S to M. Risk: none to data. Not from a line-by-line read of the crop code.

**B9. TEST deploys on a second Pages site.** The Pages site holds one build, so from 11 to 14 Nov (runs #119 to #122) the app's only address served a TEST build; anything Ray entered then went to `_Testing`. A second free repository that only deploys test branches would leave LIVE up during a test round. `isLiveBuild()` already treats any other path as "copy". Needs one more redirect URI in Entra and a manifest check. Benefit: LIVE never goes dark; no real coin typed into TEST by mistake. Size S to M, mostly Ray's setup. Risk: none to data.

# Part C: crop (added 14 Nov 2026, read-only)

Asked for by Ray after Parts A and B. Same code as the rest of this review: `app.html` at `85940b2`. Scope: both crop stages (the rectangle, Stage 1, `#bgCropOverlay`; the circle, Stage 2, `#photoAdjustOverlay`), the 90° turns and the fine angle, the circle's zoom, the rectangle's view zoom, Use Crop / Use Photo, and how an Obverse / Reverse is cut from the full-resolution original.

## The short answer

- **Nothing found that breaks (ak).** No path saves a Holder, Reference or Other photo below full resolution, re-encodes an untouched JPEG, or cuts an Obverse / Reverse from a downscaled copy. The list of what was checked is under "What looks sound".
- **The saved pixels are in the right place, but a trimmed photo is slightly softened** (C1). This is the finding most worth fixing: it is small, it touches every hand-trimmed Holder, and the fix is small.
- **The memory risk depends on the photo size** (C2). At 12 MP it is comfortable. At 50 MP each decode is about 200 MB and the app decodes more often than it needs to.
- **The tests guard the sizes well and the quality settings not at all** (T1 to T7).

## What was done, and what was not

- Read, line by line: `openPhotoAdjust` to `initPhotoAdjuster` (Stage 2: L29094-29469), the Stage 1 constants to `initBgCrop` (L29484-30218), `runCropPipeline` (L30239), `commitGalleryPhoto` (L30351), `loadOrientedImageCanvas` (L27928), the crop-from-an-uploaded-photo block (L31595-31770), `adjustStoredPhoto` (L31517), `draftRecropSource` and the Recrop handler (L32345, L32487-32515), the two other save paths (`uploadCoinDraftPhotos` L36479, `uploadStagingEditFiles` L37520), Add Set's own crop caller (L38907), and every caller of `openBgCrop`, `openPhotoAdjust`, `runCropPipeline` and `createImageBitmap`.
- Run: four throwaway probes in the session scratchpad (not committed), in headless Chromium against the real functions in `app.html`, with made-up pictures (a one-pixel checkerboard, noise, coloured quarters). Then eight "deliberately broken" copies of `app.html` in the scratchpad, each run against the 11 photo suites, to see which breaks the tests notice. The repo's own files were not changed; `npm test` was not run on the repo.
- Each finding is marked **Reproduced** (a probe showed it), **Read-only** (read in the code, not run) or **Suspected** (needs something that cannot be made to happen here, named).
- Not done: nothing on a phone. Headless Chromium on a desktop has far more memory than a phone tab and may smooth pictures a little differently from a phone's graphics chip, so the memory findings are counts and sizes, not observed crashes. No real camera photo was used. The Wishlist's photo slots (the old one-stage circle; nothing is saved from them) were read but not probed. Colour profiles were not looked at.

## What looks sound (checked, no finding)

- **Every non-flip type is trim-only**, through one function (`galleryTypeTrimOnly`), and every capture surface goes through `runCropPipeline`. The one other caller of `openBgCrop` is Add Set's child Obverse / Reverse slots, which are capped at 1400 px by rule and are cut from the original. Read-only.
- **An untouched JPEG keeps its own bytes**, including when the photo carries a camera turn (EXIF orientation). Reproduced.
- **A camera turn (EXIF orientation 6, the phone held upright) is handled everywhere in the crop path**: the screen, an untouched Holder, a trimmed Holder, an Obverse and its kept original all came out upright and with the right halves. Reproduced.
- **An Obverse / Reverse is cut from the full-resolution original**, and what is saved matches what the circle shows: with a 90° turn and a fine angle in Stage 1, then a 90° turn, a fine angle, a zoom and a pan in Stage 2, the save from the original and the screen's own picture differed by 0.03 of 255 on average. Reproduced.
- **All three save paths upload the full picture** (`entry.blob`), never the 640 px tile copy: Edit Coin / Manage Photos, Add Coin's first save, the Staging-draft edit. Read-only. (Two of the three are also guarded by tests; see T2.)
- **Recrop and crop-from-an-uploaded-photo read the full file** (the kept original for an Obverse / Reverse; the stored file's content for a Holder, never OneDrive's thumbnail). Read-only.
- **A fine-angle step and Use in the same instant** give the same result as waiting a moment: the decode at Use gives the screen time to catch up. Reproduced.
- The display copy is rounded to whole pixels on each side separately, so the map from screen to original can be out by at most half a display pixel across the whole photo. Read-only; too small to see.

## Medium

### C1. A trimmed or turned Holder is resampled, not copied, so it is slightly softened
- **What happens.** `bakeBgCropFromOriginal()` (L29741) places the crop box on the original through floating-point numbers and draws once. A finger puts the box edge between two original pixels (one display pixel is about 13 original pixels on a 4000 px photo), so every saved pixel is a blend of its neighbours. The size is right; the detail is a little softer than the original.
- **Measured (Reproduced, probe P1).** A 4000 x 3000 one-pixel checkerboard, trimmed:
  - box edges on whole original pixels: 100% of pixels still pure black or white (a perfect copy);
  - box moved by a third of an original pixel (what whole display pixels give): 0% pure, contrast 57 of 255;
  - box moved by half a pixel: uniform grey, contrast 0.
  - With two-pixel squares: 29.5% of pixels still black or white, against the 80% the existing sharpness check (K2) asks for.
- **The same for a 90° turn (Reproduced, probe P2).** A whole-photo 90° turn is an exact copy for 4000 x 3000, 4032 x 2268, 3264 x 2448 and 4080 x 3060, but not for 4000 x 2252 (a 16:9 phone size): 55% of noise pixels changed by more than 8 of 255. The cause is the same: the display copy's height rounds (900.8 to 901), and the result is stretched by a hundredth of a percent.
- **How much it matters.** Worst-case patterns are far harsher than a photograph, which has little detail at the single-pixel level. On a real Holder the effect is a slight loss of the finest detail (label microprint, hairlines), not a visible blur. Not measured on a real photo.
- **Fix.** When the total turn is 0°, 90°, 180° or 270°, round the crop to whole original pixels and copy them (no scaling, whole-pixel placement). With a fine angle a resample cannot be avoided. Size S. Test: the checkerboard with the box at an awkward position must stay 100% black and white (see T4).

### C2. Large photos are decoded more often than needed, and the "over 60 MP" guard decodes the full photo first
- **What happens.** Every decode of the original is a full bitmap in memory (width x height x 4 bytes). The counts (Reproduced, probe P4, by counting `createImageBitmap` calls):
  - a 50 MP photo (8160 x 6120) as an Obverse: **three full decodes**, about 200 MB each (opening Stage 1, Use in Stage 1, Use in Stage 2);
  - a trimmed 50 MP Holder: a full decode at open, another at Use, and at Use the output canvas is up to the same size again, so about 400 MB at the peak;
  - a 63 MP photo: `decodeFullResOriented()` (L29542) decodes it at full size just to read its width and height, closes it, then decodes it again smaller. `openBgCrop()` (L29689) also decodes at full size with no guard. So the guard that exists to protect a phone never avoids the large decode; it only avoids a large canvas afterwards.
- **Risk.** At 12 MP (4000 x 3000) each decode is 48 MB: comfortable. At 50 MP it is a real load for a phone tab. **Suspected**, not observed: whether a phone tab is killed or a canvas comes back empty depends on the device; it could not be made to happen here.
- **Also (Read-only):** `runCropPipeline` makes a link to the picked file for the kept original at the start of every crop and never releases it when the crop is cancelled. Small.
- **Fix.** Read the width and height from the file's header (or from the first decode) instead of a second decode; make the display copy with a resized decode; release the decode before encoding where possible. Size S to M.

### C3. If the circle's final encode fails, the pick is lost with nothing on screen
- **What happens.** Stage 2's Use (`initPhotoAdjuster`, L29443) encodes with `canvas.toBlob` and hands the result on without checking it. When the browser cannot encode (it gives `null`, typically when memory is short), `closePhotoAdjust()` has already run, `runCropPipeline`'s `finish()` throws on `URL.createObjectURL(null)`, and nothing is added. No message. Stage 1 does this properly (`canvasToBlob` rejects, and the crop screen stays open with "That photo couldn't be cropped").
- **Reproduced** (probe P5: the encode forced to return nothing; the circle screen closed, no entry, no toast, one uncaught error).
- **Data at risk.** The framing work, and a photo taken with the camera from inside the app, which may exist nowhere else.
- **How likely.** Low; it needs the encode to fail, which is a low-memory event (C2).
- **Fix.** Check the result before closing; on failure keep the circle screen open and say so, as Stage 1 does. Size S.

## Low

### C4. An empty result would be saved as the photo (Suspected)
When a phone cannot give a canvas its memory, drawing does nothing and the encode can still produce a valid, plain black JPEG. Nothing checks that the result has a picture in it, so a black Holder or Obverse would be saved. A Replace never deletes the old file, so the old photo would still be in OneDrive. **Suspected**: it needs a real low-memory failure. Fix: compare a small copy of the result with the display copy and refuse an all-black result from a picture that is not black. Size S.

### C5. The "over 60 MP" guard makes a near-square photo bigger
`decodeFullResOriented()` scales the long edge to 8192 without checking that this is smaller. A photo over 60 MP whose long edge is under 8192 is enlarged. **Reproduced** (probe P4: 7800 x 7800, 61 MP, decoded at 8192 x 8192, 67 MP, and saved at 8051 x 8192 with the "kept at 8192 px" message). Only near-square photos between 60 and 67 MP; rare. Fix: never scale up (one `Math.min(1, ...)`). Size S.

### C6. A very small trim is thrown away
`bgCropUntouched()` (L29724) calls the box "the whole photo" when every edge is within half a display pixel of the photo's edge. At 4x view zoom a handle dragged 2 screen pixels moves the box by exactly half a display pixel: the screen shows a 2 px shaded strip, and Use keeps the whole original. **Reproduced** (probe P3: a real pointer drag of 2 px at 4x gave "original-bytes"; in original pixels the ignored trim was up to 6.7 px of 4000). Harmless direction (nothing is lost), but the screen and the file disagree, and the view zoom exists for exactly this kind of fine trim. Fix: a far smaller tolerance (the box only ever differs from the whole photo by rounding noise when it was not moved). Size S.

### C7. After a Stage 1 fine turn, the circle can show a sliver of black
The margin Stage 1 hands to the circle (`bgCropHandOffRect`, L29782) stops at the edge of the turned photo's outer rectangle, which has empty corners. With a 10° turn and a box wholly on the photo near its edge, zooming the circle out put 1.9% black inside the saved circle. **Reproduced** (probe P7). The screen shows the same black, so nothing is hidden; it is the (bs) rule "the circle must never show black" that this case slips past (the rule's tests cover the picture's edge, not its empty corners). Fix: limit the margin, or the circle's zoom-out, to the photo itself. Size S to M.

### C8. A PNG with a see-through background is saved with a black one, and an untouched PNG is re-encoded
An untouched trim-only pick keeps its bytes only when it is a JPEG. Anything else is drawn and saved as a JPEG at 0.95, and see-through areas come out black. **Reproduced** (probe Q7: the transparent half of a PNG Reference was black in the saved file). A grading service's cut-out coin image is the likely case. Fix: paint white first. Size S.

### C9. The kept original of a non-JPEG Obverse is named .jpg
The kept original is the picked file's own bytes under `{ID}_obverse_original.jpg`, whatever the file is. **Reproduced** (probe Q7: PNG bytes, 89 50 4E 47, under a .jpg name). Browsers and the app read it by content, so it displays; other tools may not. Cosmetic.

### C10. A file that will not decode opens nothing and says nothing
`runCropPipeline` calls `openBgCrop` without catching its failure. The library and Files paths test the file first (`isPickableImage`); the camera path and the older two-button photo slots do not. **Reproduced** (probe Q1: no crop screen, no toast, one unhandled error). No data risk. Fix: one catch with the existing "couldn't be cropped" message. Size S.

### C11. An untouched Holder keeps everything the camera put in the file (Read-only)
This follows from keeping the original bytes and is not a fault: the file keeps the camera's own data, which includes the place the photo was taken if the camera records it, and a Samsung "motion photo" keeps its short video inside the file (which also explains some very large Holder files). The files are in Ray's own OneDrive and the app's sharing does not attach photos today. Worth knowing before any feature that sends a stored photo to someone else.

## Gaps in the tests

Found by breaking a scratchpad copy of `app.html` one way at a time and running the 11 photo suites (`photo_fullres`, `crop_basics`, `guided_crop`, `crop_from_upload`, `photos_wait_for_save`, `addcoin_shared_photos`, `staging_edit_photos`, `photo_receipt_write`, `replace_never_overwrites`, `addcoin_phase1`, `staging_edit`; 912 checks, all passing unbroken).

- **T1. The JPEG quality settings are not guarded.** Trim quality 0.95 changed to 0.5: all 912 checks passed. Obverse / Reverse quality 0.92 changed to 0.5: all 912 passed. A slip here would make every new photo visibly worse with the suite green.
- **T2. The Staging-draft edit's save can upload the tile copy unnoticed.** That save changed to upload the 640 px tile instead of the full picture: all 912 passed. The same break in Edit Coin's save and in Add Coin's first save was caught.
- **T3. Crop-from-an-uploaded-photo on a draft can read the tile copy unnoticed.** The draft branch of `loadCropSourceBlob` changed to use the tile: all 912 passed. The same break for a saved record was caught (E1).
- **T4. The sharpness check cannot see C1.** K's box sits exactly on whole original pixels (a quarter and three quarters of the photo), which is the one position where a trim is a perfect copy.
- **T5. No crop suite uses a photo with a camera turn (EXIF orientation).** The behaviour is right today (probe P6); nothing would notice if it stopped being right. Only the viewer's suite touches orientation.
- **T6. The "untouched" tolerance is guarded by accident.** Raised from 0.5 to 6 display pixels it was caught, but only because the 63 MP test happens to trim by one display pixel; any value under 1 passes.
- **T7. No test for C3 (a failed encode) or C5 (a near-square 60 MP photo).**
- **Seen in passing, for Build 1:** with four of these runs sharing the machine, `crop_from_upload` D4 and D5 failed twice and passed when run alone. It is a timing wobble under load, the kind the parallel runner will have to deal with.
